## 1. 背景

- Silverでは、社員ごと・作業日ごとに承認済みの実績を作る。社員を何で見分けるかによって、「社員日（だれの・何日の作業か）」のまとまりや、社員別明細・負荷バランスの結果が変わる。
- 以前は company_cd + mhi_emp_no（会社コード＋従業員番号）を第一候補にしていた。従業員番号は他の社員に再利用されず、会社をまたいで同じ人を追う必要もない（本人確認済み）。
- テーブル仕様書では、3ビューとも mhi_emp_no と user_id は必須（NOT NULL）。しかし実データには、mhi_emp_no が空欄の行がある。

## 2. 判断のもとになった事実

会社AAA、V_T_OKS02 の全期間（9月の数字は2026年9月分）。

| 観察したこと | 件数 |
| --- | --- |
| user_id の総数 | 4,629 |
| 従業員番号が1つだけの user_id | 4,577 |
| 従業員番号が2つある user_id | 52 |
| └ 片方が空欄 | 48（うち42は期間が重なる＝番号がところどころ抜けているとみられる） |
| └ 番号が別の番号に変わった | 3 |
| └ 2つの番号の期間が重なる | 1 |
| user_id が2つある従業員番号 | 2（切り替え1、期間が重なる1） |
| 従業員番号が空欄の行を持つ user_id | 51 |
| 2026年9月の空欄の行 | 46行（machine_flg=0：43行、machine_flg=1：3行） |
| 2026年9月の照合で、空欄が原因で起きたずれ | 9社員日（別の人が1人にまとまった） |

- user_id は、工数システムのログイン・変更者・承認者の記録に使われている（定数ファイル [KeijoKosuConstants.java](../spec/source/KeijoKosuConstants.java) の LOGIN_USER_ID、V_T_OKS10 の update_user_id）。
- 定数ファイルにはユーザ種別（1＝社員、3＝労派、4＝請負、9＝その他、null＝退職者）の定義があるが、3ビューにはユーザ種別のカラムがない。従業員番号が空欄の理由はデータでは確かめられない。

## 3. 検討した選択肢

### A：company_cd + user_id（採用）

- 良い点：従業員番号が空欄の人も1人ずつ見分けられる。番号がところどころ空欄の人も1人のまま。工数システム自体がユーザIDで動いている。
- 悪い点：user_id が切り替わった人は2人に分かれる。人事・権限などのデータが従業員番号を持つ場合、つなぐには従業員番号を経由する必要がある。user_id が別の人に再利用されていた場合、2人が1人にまとまる（→ 2026-10-27の確認で、再利用の例は見つからなかった。§7参照）。

### B：company_cd + mhi_emp_no（不採用）

- 良い点：従業員番号は再利用されないと本人確認済み。user_id が切り替わっても1人のまま。他のデータとそのままつなげる。
- 悪い点：空欄の人たち（51ユーザ分）が「空欄の1人」にまとまる。番号がところどころ空欄の人（42ユーザ）は、同じ人が2人に分かれる。仕様書では必須なのに、実データと合わない。

## 4. 使い道ごとの比較

| 使い道 | A：ユーザID | B：従業員番号 |
| --- | --- | --- |
| 月次実績・社員別明細 | user_id を切り替えた1名が2行に分かれる | 空欄の人がまとまった「架空の1人」が出る |
| 負荷バランス（社員間の偏り） | 切り替えた月に1人の工数が少なく見える | 架空の1人に工数が集まり、偏りがあるように見える（影響大） |
| 計上先変更の対応確認 | 対象者の指示がどちらの番号で出ているかによる（未確認） | 同左 |
| 閲覧範囲の制御・他データとの結合 | 保持した mhi_emp_no でつなぐ。空欄の人はつなげない | そのままつなげる。空欄の人はつなげない |
| 会社をまたいだ同一人物の追跡 | 不要（本人確認済み） | 不要（本人確認済み） |

## 5. 決定

- **Silverでは、社員を company_cd + user_id で識別する。**
- mhi_emp_no は作業日当時の値として保持し、他のデータとの結合や閲覧範囲の制御に使えるようにする。
- 決め手：Bでは従業員番号が空欄の人たちが1人にまとまり、負荷バランスで架空の高負荷者が出る。この害は、Aで「user_id を切り替えた人が2人に分かれる」害より大きい。どちらの案でも、うまく扱えないのは4,629ユーザのうち数十件。

## 6. この決定で起きること

良くなること

- 従業員番号が空欄の51ユーザが、別々の人として数えられる。2026年9月の照合で出た9社員日のずれは解消する見込み。
- 番号がところどころ空欄の42ユーザが、1人のまま数えられる。

受け入れること

- user_id が切り替わった社員1名と、2つの user_id の期間が重なる社員1名は、それぞれ2人として数えられる。必要になったら対応表で名寄せする。
- 他のデータとは mhi_emp_no 経由でつなぐ。空欄の人はつなげない。
- 以前の第一候補（mhi_emp_no）を置き換えるため、関連ページの記載を更新する。

## 7. 前提と見直す条件

前提（2026-10-27にデータで確認済み、会社AAA）

1. user_id に空欄がないこと。→ **確認済み**。V_T_OKS02・V_T_OKS07・V_T_OKS10 のいずれも、user_id が空欄またはNULLの行は0行。
2. user_id が別の人に再利用されていないこと。→ **確認済み**。V_T_OKS02 で空欄以外の従業員番号が2つある user_id は4件（番号が別の番号に変わった3件＋2つの番号の期間が重なる1件）。いずれも sei_mei（氏名）は1種類だけで、同じ人の従業員番号が変わったと考えられる。同姓同名の別人という可能性は残るが、低いと判断。

補足：この4人は、B案（従業員番号で識別）だと2人ずつに分かれていた。A案では1人のまま数えられる。

見直す条件

- 上の前提が崩れたとき。
- Silverの利用先で、従業員番号単位の集計（人事データとの突き合わせなど）が必須になったとき。
- 担当者から、user_id の付け替え・再利用のルールが示されたとき。

見直すときの候補（未評価）：従業員番号を優先し、空欄のときだけ user_id を使う案。

## 8. この決定の範囲外

- mhi_emp_no の空欄を、同じ user_id の他の行の番号で補うか。
- machine_flg=1 の行を分析に含めるか。
- 所属などを作業日当時の値で持つか。
