## 1. 背景

工数データには2つのニーズがある。

- 承認済みかどうかに関わらず、最新の入力状況を知りたい。
- 承認された状態を知りたい。

どちらか一方に決めきれていなかった。V_T_OKS02は最新の入力だけを持つ単断面なので、承認済みの明細を直すと旧版がビューから消える。一方、変更履歴（V_T_OKS10）を日次処理の入力にすると、履歴の整理と組の判定が必要になり、構成が重くなる。

## 2. 判断のもとになった事実

会社AAA全期間（1,297,001社員日、抽出時点）の[サンプルデータ](../research/sample-data.md)集計2より。

| 状態 | 社員日 | statusで絞った結果 |
| --- | --- | --- |
| 新規の承認待ち（過去に承認済みなし） | 4,100 | 正しい（実績なし） |
| 承認後の再編集が承認待ち | 60（約0.005%） | 旧承認値が欠ける |

- 2026年9月分は、締切後の時点でも167社員日（約0.2%）に承認待ちが残っていた（集計5）。締切を過ぎると2つの見え方はほぼ一致する。
- OKS02のstatusは、2026年9月のずれた1,732社員日では社員日の中で同じ値だった（集計5）。全体は未確認。
- 同じ明細が2本のfactに出ても、キーは同じ計算で揃えられる。

## 3. 世の中の例

SAPの工数管理（CATS）は、承認済みの記録を変更すると、元の記録を「変更済み」の状態で残し、新しい記録が承認されるまで置き換えない。外部へ渡すのは承認済みと取消の記録である（古い版の公式資料で確認）。同じ明細の版を2つ持つ考え方は、今回の承認ゲートと同じである。

dbtのスナップショットのように、上書きされる表を定期的に写して履歴を作る方法も定番である。

## 4. 検討した選択肢

### 4.1 見せ方

| 案 | 内容 | 評価 |
| --- | --- | --- |
| fact 2本（採用） | 同じ粒度・共通dimensionで用途別に分ける | 1行の意味が明快。既存の「実績factには混ぜない」と整合 |
| 1行に2つの数値 | latest_hoursとapproved_hours | 差は出しやすいが、属性が版で異なるときの扱いが要る。比較ビューで代替できる |
| 版の種類を列で持つ | 同じ明細が2行になる | 絞り忘れると二重計上する |
| 状態列で絞る | 1表＋status | 再編集中の明細で旧承認値が欠ける |

### 4.2 承認済みの作り方

| 案 | 内容 | 評価 |
| --- | --- | --- |
| 承認ゲート（採用） | 日々の単断面を社員日単位で判定し、前回の承認済みを保持する | OKS10なしで済む。前回の状態に依存する |
| OKS10から作る | ADR-002までの手順 | 精度は高いが、履歴の整理が日次で要る |
| statusで絞るだけ | 保持しない | 最も単純だが、承認待ちの間だけ実績が減る |

## 5. 決定

1. **Silverの公開factは2本にする。** fact_work_actual（承認済み）とfact_work_latest（最新の入力）。粒度・キー・dimensionを揃え、合算しない。差は比較ビューで出す。
2. **最新の入力はOKS02の単断面から作る。** 締切後の修正（OKS07）は、承認待ちも含めて重ねる。
3. **承認済みは社員日単位の承認ゲートで作る。**

| 今日の単断面 | 承認済みの扱い |
| --- | --- |
| 社員日の全行がstatus 4〜7 | 今日の行で置き換える |
| 承認待ち（status 1〜3）の行を含む | 前回の承認済みを維持する |
| その日の全件の単断面に社員日の行がない | 実績なしとする |

4. **締切後の修正（OKS07）は、status 4〜7だけを承認済みに重ねる。** OKS02は修正をほとんど反映しないため、置き換えのたびに当て直す。
5. **OKS10は日次処理に使わない。** 用途は、差分量のヒント、承認ゲートの検証、初回の補完に限る。

## 6. この決定で起きること

良くなること

- 2つのニーズに、それぞれ答えられる。
- 実績の数字が、承認待ちの間だけ減ることがない。
- 日次処理からOKS10の履歴整理がなくなる。

受け入れること

- Silverが前回の状態に依存する。作り直すには、日々の単断面を保持する必要がある。案1では日次CSVの長期保管が要り、案2ではBronzeが履歴を兼ねる。
- 行が消えたとき、削除の承認待ちと承認済みを区別できない。影響しそうな社員日は現データで2件（集計2のB1のみ・過去A4あり）。
- 同じ日に承認と再編集が続くと、旧承認値を取り逃す。
- 記録開始時に再編集中の社員日は、OKS10で補う。

## 7. 前提と見直す条件

未確認の前提

- OKS02のstatusは、全体でも社員日の中で揃う。
- 締切後の修正は、OKS02の明細にも照合キー9列で当たる。これまでの検証はOKS10から作った状態が相手だった。
- OKS02だけ行がない30社員日（2026年9月）の原因が、この方式を壊さない。
- 最新の入力の利用者がいる。いなければfact_work_latestは後回しにする。

見直す条件

- シミュレーションで、承認ゲートの結果がOKS10から作った正解と説明できない形でずれたとき。
- 上の前提が崩れたとき。
- 再編集中の社員日が想定より大幅に多いと分かったとき。
