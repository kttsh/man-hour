# 工数モデリング｜学習の要点

> [!NOTE]
> **モデリングは、「何を知りたいか」から、残す情報の単位と意味を決めること。**
>
> 基本概念と、Bronze・Silver設計で学んだ要点をまとめる。詳細な仕様・検証記録は末尾の正本を参照する。

## 1. 分析目的から粒度を決める

- **考える順序：** 業務プロセス → 粒度 → dimension → factに持つ数値。
- **粒度は「1行が何を表すか」。** 月次で集計したくても、社員別・作業別に確認するための明細は残す。
- 同じ社員・日付・計上先でも、作業分類などが違えば別行にする必要がある。元の全項目を機械的に粒度へ追加するのではなく、分析に必要な区別を選ぶ。

| 用語 | 役割 |
| --- | --- |
| fact | 工数など、出来事・状態に対応する数値を記録する |
| dimension | 社員・日付・計上先・作業分類など、分析の切り口を表す |
| 業務キー | 業務上の対象を識別するコード。会社など、識別できる範囲も確認する |
| サロゲートキー | 分析用の識別子。付けるだけでは重複や粒度の曖昧さは解消しない |

dimensionの属性を上書きするか、変更ごとのバージョンを残すかで、1行の意味も変わる。履歴を持つなら、factがどの時点の行を参照するかまで決める。

> [!IMPORTANT]
> **判断の問い：この違いをまとめても、知りたいことに答えられるか？**

## 2. Bronzeの保持と、Silverの採用を分ける

**取得元3ビュー → DataSpiderでCSV出力 → GCS → 外部テーブル＋Dataform → Bronze → Silver**

| 層 | 今回の方針と学び |
| --- | --- |
| Bronze | CSVの全行・全列を取得回ごとに蓄積。0時間・NULL・重複も削らず、元の記録を残す |
| Silver | 承認済み実績のfactと分析の切り口を作る。ビュー1本＝fact1本とは限らない |

**CSVの全行を残すことと、取得元全体の全件が届くことは別。** ビューの収録範囲とCSVの抽出範囲も分けて確認する。

## 3. 実績の日付・状態・更新単位をそろえる

- **作業日・修正日・取込日は別。** 実績は作業日基準。status 4〜7を承認済みとし、未承認中は旧承認済み値を残す。
- ビュー1本＝fact1本とは限らない。どのビューから実績を作るかは、ビューごとの収録内容を確かめて決める。
- 修正の値が差分か修正後の値かを確かめる。修正後の値なら、修正前後を足さない。

> [!NOTE]
> **4月の3時間を6月に5時間へ修正したら：**
>
> 承認前は「4月・3時間」、承認後は「4月・5時間」。8時間にはしない。

社員の識別、粒度、照合キー、置換範囲、名称・所属の今回の決定は[Silverコンセプト](../spec/silver/concept.md)にある。

## 4. 履歴の整理と、実績の採用を分ける

- 同じ履歴の繰り返し受信は、工数の追加ではない。全列一致だけでは、statusが変わった同じ履歴を別件として残してしまう。
- **0時間は最新状態を作った後に除外する。** 先に除くと取消を見落とし、旧実績が残る。NULLは0とみなさない。
- 作業明細の削除と履歴の削除は別。CSVに行がないだけで削除と判断しない。

## 5. 工数・原価管理の用語

| 用語 | 捉え方 |
| --- | --- |
| 原価センタ | どの部門などで原価を管理するか |
| OPA（内部指図） | 何の目的・活動の原価を管理するか |
| WBS要素 | どの案件の、どの作業を管理するか |
| 利益センタ | どの事業などの損益として捉えるか |
| 活動タイプ | 原価管理上の活動の種類。作業分類とは別の切り口 |
| 活動価格 | 活動量を原価へ換算する単価。個人の時給とは限らない |

**工数 × 活動価格 ＝ 原価の評価額。** 今回の3ビューには活動価格・原価金額がなく、金額の算出には適用期間・提供元・価格単位などの追加情報が必要。

> [!IMPORTANT]
> **一般的な用語の意味と社内運用を混同しない。**
>
> 原価センタ・OPA・WBS・利益センタは一本の階層ではない。今回の入力ルールは「WBS・OPA・原価センタのいずれか一つに計上する」。関連情報として保持する列とは区別する。

## 6. 設計を確かめる視点

- キーは業務ルールと実データで確認する。サンプルで一意でも、将来の保証とは限らない。
- factとdimensionの結合で、件数・合計工数が増えないことを確認する。
- 修正・取消・再取込で二重計上や欠落がなく、必要な分析ができるかを検証する。

> [!WARNING]
> **事実・要件・設計案・未確認事項を分ける。仕様書への記載と実装・動作検証の完了も別。**
>
> C案のIDの安定性・再利用・同順位競合、CSVの取得範囲などは未確認事項として残る。詳細はSilverコンセプトとADRで管理する。
