# 事前準備タスク｜工数データ取込方式の比較

> [!IMPORTANT]
> **決めたいこと：工数データ出力（V_T_OKS02）を、毎日の入れ替えで作るか（案1）、差分の積み上げで作るか（案2）**
>
> V_T_OKS02は、ある時点の最新状態だけを持つ単断面である。比較の軸は、この単断面の扱い方の2案に置く。
>
> BigQueryの処理量・コストを比較して判断する。**コスト差がわずかなら、案1を採用する。**

このページは案の定義、時系列、判断ルール、把握済みの件数の正本である。何をどう測るかは[更新方式シミュレーションの要求事項](update-method-simulation-requirements.md)に書く。

**現状：** 方式決定・コスト算出は未実施。件数調査は4〜8月分の土台と9/12時点の評価のみ。

## 2案の軸

| 比較点 | 案1：単断面の入れ替え（達磨方式） | 案2：差分の積み上げ |
| --- | --- | --- |
| 毎日届くCSV | 当月の月初から取得日までの全行 | その日に新規・更新された行 |
| 変更のない行 | 毎日取り直す | 取り直さない |
| Bronze | 当月分をまとめて置換。過去月は触らない | 受信した全行を追加保存 |
| Silver | テーブル更新（当月分の入れ替え）。構成が単純 | incremental更新。変更データから正のデータを取り出す |
| 過去月の修正 | 触らない | 計上月で絞らず、対象時間内の更新を受ける |
| **主なリスク・コスト** | **その月の間は、ずっと入れ替わり続ける** | **最新の情報がどれかを探すコストがかかる** |

案1は、テーブル全体の置換でも、当月累積CSVの取得回別追加保存でもない。案2は、社員日全体や履歴の最新の組だけを選ぶ方式でもない。受信した全行をBronzeに持ち、Silverで処理する。

## 3ビューの役割

| ビュー | この比較での役割 |

| V_T_OKS02（工数データ出力） | 比較の主対象 |

## 案1の時系列

| 取得日（例） | 届くCSV | Bronzeで入れ替える範囲 | そのまま残す範囲 |
| --- | --- | --- | --- |
| 9/1 | 9/1分の全データ | 9月分 | 8月以前 |
| 9/5 | 9/1〜9/5分の全データ | 9月分 | 8月以前 |
| 9/30 | 9/1〜9/30分の全データ | 9月分 | 8月以前 |
| 10/1 | 10/1分の全データ | 10月分 | 9月以前 |
| 10/5 | 10/1〜10/5分の全データ | 10月分 | 9月以前 |

当月内の既存データの修正は、その日の当月累積CSVで反映する。過去月を触らないことによる遡及修正への影響は調査事項とする。過去月も更新する仕様へ勝手に変更しない。

## 案2の時系列

比較の前提として、2026年4月以降の過去データは投入済みとして扱う。初回取込の設計は対象外とする。実際の取込先の格納状態を確認した意味ではない。

| 場面 | CSVの取得範囲 | Bronze | Silver |
| --- | --- | --- | --- |
| 日次更新前の状態 | 過去分の新規取得は対象外 | 4月以降の過去データが入っている前提 | 過去データが反映されている前提 |
| 毎日6:00の日次更新 | 前回6:00以上〜今回6:00未満に新規・更新された行（整理案） | 受信した全行を追加保存 | 新規は追加。過去日付の変更は、ステータスを考慮して採用すべき最新データへ更新 |
| 新規・更新なし | CSVは届かない（[Bronze](../spec/bronze/concept.md)の0件CSVの前提） | 追加なし | 他に要因がなければ変更なし |
| 月替わり | 日次の取得条件を継続（整理案） | 過去の取得分を保持 | 固有の処理の要否は未確定 |
| 過去月修正 | 計上月で絞らず、対象時間内の更新を取得（整理案） | 修正後の行を追加保存 | 変更に関係する日または月を特定し、最新データへ更新 |

### 案2のSilver：全件を読まず、対象を絞って最新を探す

蓄積済みの全データを毎日読み直す方式を前提にしない。日付別または月別の台帳で、更新に関係する範囲を特定する。

| 順番 | 処理 | 読取範囲の考え方 |
| --- | --- | --- |
| ① | 今回取り込んだ新規・更新行を読む | Bronzeの今回取得分に限定する。識別方法は未確定 |
| ② | 変更に関係する日付・月と更新対象を特定する | 台帳を利用する構想。台帳の意味・保持項目・区切る日付列は未確定 |
| ③ | 新規の行を追加する | 新規の判定方法は未確定。同じ日付の既存行があるだけで変更扱いにはしない |
| ④ | 過去日付の変更を反映する | 対象範囲の既存データから最新を探して更新する。ここが探索コストになる |

**検証事項：** 日・月で台帳を区切るだけでBigQueryの読取量が減るとは限らない。台帳で特定した範囲を実際のクエリの絞込み条件に反映し、読取バイト数で効果を確かめる。台帳そのものの読取量も比較に含める。

## 費用の計算

**費用（USD）＝課金対象データ量（TiB）× $7.5。** 課金対象バイト数 ÷ 1,099,511,627,776 × 7.5で算出する。

$7.5／TiBはユーザー指定の試算前提である。件数やCSV容量ではなく、実行ジョブのtotal_bytes_billedで算出し、日次処理の対象ジョブを合計して1日分・月間分を比べる。無料枠・契約割引の適用前の試算とし、保存・取込等の費用は別に扱う。

## Dataform取込処理の留意事項

- クラスタリング・パーティションをkeijo_date軸にして、案1・案2の分割方法を検討する。keijo_dateはBronzeではSTRINGなので、パーティションには派生列が要る。
- keijo_date軸の部分テーブル更新を検討する。案1は月パーティションが使えると運用しやすくなる見込みだが、適用可否と効果は未検証。
- 締切済工数修正の差分更新（Bronze→Silver）は、両案とも独立したworkflowを作る。

## 比較中に変えない前提

- 案1で入れ替えるのは当月分だけ。テーブル全体は置換せず、過去月分はそのまま残す。
- CSV件数だけでコストを判断しない。CSV出力、Bronze取込、Silver処理を分けて把握する。
- 方式が決まるまで、取込方針に関わる仕様は変更しない。既存のBronze仕様は取得回別の追加保存であり、案1とは異なる。
- 参照環境は継続更新される前提で進める。ただし他の資料と記述が割れているため、要求事項のA-01で確かめる。

## 未確定

登録・更新日時の時刻基準、再取得時の扱い、Silverで同じ行を識別するキー、ステータス別の採用条件と新旧判定、0工数化・削除の反映、台帳の区切りと構成、月パーティションの適用可否。「最新」を更新日時だけで決めるとはまだ定めない。
