# 事前準備タスク｜工数データ取込方式の比較

> [!IMPORTANT]
> **決めたいこと：工数データの取込方式を、案1・案2のどちらにするか**
>
> BigQueryの処理量・コストを比較して判断する。**コスト差がわずかなら、案1を採用する。**

## まず押さえる3点

| ポイント | 要点 |
| --- | --- |
| **何が違う？** | **案1＝当月全件を毎日取り直す。案2＝その日に新規・更新されたレコードだけを取得する。** |
| **何を比べる？** | CSV件数だけでなく、Bronzeへの取込・保持と、Silverの読取・更新にかかる処理量・コストを比べる。 |
| **今、何をする？** | **案2の日々の動きと、両案のSilverの処理範囲を整理する。** その後、SQL Serverで件数を調べる。 |

## 進める順番

| 順番 | やること | この段階で明らかにすること |
| --- | --- | --- |
| **① 今ここ：動きを整理** | 案2の時系列と、両案のSilverの処理範囲を決める | 何を取得・保存・読み取り・更新するか |
| **② SQL Serverで調査** | 当月全件数・日次更新件数・過去月更新の内訳等を調べる | 各案で扱うデータの量と範囲 |
| **③ BigQueryで測定・比較** | 実CSV容量、取込・保持量、Silverの読取量等を測定する | 処理量・コストの差と採用案 |

**現状：方式決定・件数調査・コスト算出はいずれも未実施。**

> [!WARNING]
> **比較中に変えない前提**
>
> - **案1で入れ替えるのは当月分だけ。** テーブル全体は置換せず、過去月分はそのまま残す。
> - **CSV件数だけでコストを判断しない。** Silverの処理範囲も確認する。
> - **方式が決まるまで、既存の仕様書は変更しない。**

## 確認済みの前提

- SQL Serverの参照環境は継続更新される。
- 案1は、当月の月初から取得日までの全レコードを毎日CSV化し、Bronzeの当月分をすべて入れ替える。過去月分はそのまま残し、触らない。
- 案1は、テーブル全体の置換でも、当月累積CSVの取得回別追加保存でもない。
- 案2は、その日に新規・更新されたレコードを取得する。社員日全体や履歴の最新の組だけを選ぶ、という意味ではない。受信した全レコードをBronzeに保持し、Silverで処理する比較案。詳細な保持・採用方法は今後整理する。
- まず時系列と調査項目を詰める。更新前後の実データ検証や実装を先に進めるのではなく、SQL Serverで必要な情報を調べ、その結果をBigQueryのコスト検討につなげる。

## 案1の時系列：当月累積データで当月分だけを置換

| 取得日（例） | 届くCSV | Bronzeで入れ替える範囲 | そのまま残す範囲 |
| --- | --- | --- | --- |
| 9/1 | 9/1分の全データ | 9月分 | 8月以前 |
| 9/5 | 9/1〜9/5分の全データ | 9月分 | 8月以前 |
| 9/30 | 9/1〜9/30分の全データ | 9月分 | 8月以前 |
| 10/1 | 10/1分の全データ | 10月分 | 9月以前 |
| 10/5 | 10/1〜10/5分の全データ | 10月分 | 9月以前 |

当月内の既存データの修正は、その日の当月累積CSVに含まれる内容で反映する想定。過去月を触らない場合の遡及修正への影響は調査事項とし、過去月も更新する仕様へ勝手に変更しない。月パーティションの適用可否・効果は未検証。

## 案2の時系列：過去データが入っている状態から日次更新

> [!IMPORTANT]
> **比較の前提：2026年4月以降の過去データは、すでに入っているものとして扱う。初回取込の設計は今回の整理対象にしない。**
>
> 毎日6:00に新規・更新分を取得する。9月の日次比較では、4～8月分を既存データの土台とし、その月別件数・合計件数もSQL Serverで調べる。これは比較用の前提であり、実際の取込先の格納状態を確認済みという意味ではない。

| 場面 | CSVの取得範囲 | Bronze | Silver |
| --- | --- | --- | --- |
| **日次更新前の状態** | 過去分の新規取得は今回の対象外 | 4月以降の過去データが入っている前提。9月比較の土台となる4～8月分の件数を調べる | 過去データが反映されている前提。日付別または月別の台帳管理で、日次処理の対象範囲を限定する方針 |
| **毎日6:00の日次更新** | 前回6:00以上～今回6:00未満に新規・更新されたレコードを取得する整理案 | 受信した全レコードを追加保存し、以前の取得分も保持 | 新規は追加。過去日付の変更はステータスを考慮して採用すべき最新データへ更新。台帳を利用して対象範囲に絞る |
| **新規・更新なし** | 0件 | 追加なし | 他に処理要因がなければ変更なし |
| **月替わり** | 日次の取得条件を継続する整理案 | 過去の取得分を保持 | 月替わり固有の処理の要否は未確定 |
| **過去月修正** | 計上月で絞らず、対象時間内の更新を取得する整理案 | 修正後のレコードを追加保存 | 変更に関係する日または月を特定し、ステータスを考慮して最新データへ更新する方針。具体的な絞込み方法は未確定 |

**未確定：** 登録・更新日時の時刻基準、再取得時の扱い、Silverで同一レコードを識別するキー、ステータス別の採用条件と新旧判定、0工数化・削除の反映。日次の抽出条件は件数調査用の仮条件と実運用の確定条件を区別する。

### 案2のSilver：全件を読まず、対象を絞って更新する

> [!IMPORTANT]
> **新規は追加、過去日付の変更は変更履歴ビュー（V_T_OKS10）も確認し、ステータスを考慮して整合する最新データへ更新する。**
>
> 日付別または月別の台帳管理を検討し、更新に関係する範囲を特定する。蓄積済みの全データを毎日読み直す方式を前提にしない。変更履歴の参照も対象範囲に絞る方針とし、具体条件は未確定。
>
> **今回の比較での違い：案1は当月分を全件洗い替えるため、その置換のための変更履歴確認は不要。案2は差分で既存データを更新するため、変更履歴確認を処理とコストの両方に含める。** 案1の過去月を更新しない前提は変えない。

| 順番 | 処理 | 読取範囲の考え方 |
| --- | --- | --- |
| ① | 今回取り込んだ新規・更新レコードを読む | Bronzeの今回取得分を識別して限定する。具体的な識別方法は未確定 |
| ② | 変更に関係する日付・月と更新対象を特定する | 日別または月別の台帳を利用する構想。台帳の意味・保持項目・区切る日付列は未確定 |
| ③ | 新規レコードを追加する | 新規の判定方法は未確定。同じ日付の既存レコードがあるだけで変更扱いにはしない |
| ④ | 変更履歴を確認し、過去日付の変更を反映する | 対象範囲の既存データとV_T_OKS10を確認し、ステータスと履歴に基づいて採用状態を判定して更新する。履歴の具体的な参照範囲は未確定 |

**検証事項：** 日・月で台帳を区切るだけでBigQueryの読取量が減るとは限らない。台帳で特定した対象範囲を、実際の読取・更新クエリの絞込み条件に反映し、読取バイト数で効果を確認する。台帳そのものの読取量も比較に含める。

**次に決めること：** 台帳を区切る日付列と日次／月次の粒度、台帳の構成、同一レコードの識別キー、ステータス別の採用条件。「最新」を更新日時だけで決めるとはまだ定めない。

## 2案の差と、調査に必要な情報

| 比較点 | 案1：当月全件の洗い替え | 案2：日次更新レコードの取得 | 必要な情報 |
| --- | --- | --- | --- |
| CSVの範囲 | 月初〜取得日までの当月全件 | その日に新規・更新されたレコード | 同じ取得日の当月全件数と日次更新件数 |
| 変更のない行 | 毎日再取得 | 再取得しない | 当月全件数と更新件数の関係 |
| 変更履歴の確認 | 当月分の全件洗い替えのための履歴確認は不要 | V_T_OKS10も参照し、ステータス・履歴を踏まえて既存データとの整合を取る | 案2で必要な履歴の取得・読取件数、参照範囲、処理量 |
| Bronze | 当月分をまとめて置換、過去月は保持 | 受信レコードを保持。詳細は整理待ち | 保存・再受信・採用のルール |
| 過去月 | 触らない | 過去月の更新も抽出条件に含むか確認 | 日次更新分の作業月別内訳 |
| Silver | 親ページではテーブル更新案。具体的な読取・置換範囲は整理待ち | 新規は追加。過去日付の変更はステータスを考慮して更新。日別／月別台帳による対象範囲の限定を検討 | 今回取得分・台帳・既存データの読取範囲と更新対象 |

CSV件数だけでBigQueryのコストを判断せず、CSV出力・Bronze取込・Silver処理を分けて把握する。
