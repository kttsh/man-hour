## 2. 2案で測ること

### 2.1 案1：どれだけ入れ替わり続けるか

毎日の入れ替えで、行がどれだけ実際に変わるかを測る。変わらない行が大半なら、入れ替わり続けることの実害は読み書きの量だけになる。月末近くまで値が大きく動くなら、月中の数字をどう見せるかが論点になる。

もう1点、案1の定義から導かれる事実を確かめる。9月分を最後に入れ替えるのは9/30の実行なので、それより後の変化は月を過ぎると届かない。

| 変化 | 根拠 |
| --- | --- |
| 月末当日の入力 | 実行は6:00 |
| 翌月に入ってからの前月分の入力 | 作業日20260106の入力が2026-01-08の例あり |
| 締切によるstatus更新 | 9月分の事例はupdate_dateが2026-10-01 10:16、status 6 |

入れ替わり続けるリスクとは別の話なので、影響の大きさを別に数える。空白に入る行数はまだ数えていない。

### 2.2 案2：どれだけ届くか

差分の量は変更履歴をヒントに見積もる。ただしOKS10の行数は、OKS02の差分の行数そのものではない。ずれは両方向にある。

| ずれ | 理由 | 根拠 |
| --- | --- | --- |
| 多く見える | 1回の保存でB行とA行を書き、変更していない明細も書く | 2026年9月2日の例は、1明細の変更で1回の保存につき4行 |
| 多く見える | 同じ明細を何度変えても、OKS02では1行 | 比較資料の評価メモ |
| 少なく見える | 承認・締切では履歴の行が増えず、OKS02のupdate_dateだけが動く可能性 | 2026年9月1日の例は、OKS10が4行のまま、OKS02のupdate_dateだけ2026-10-01 |

最後の項目が差分の量を左右する。更新日時で差分を取ると、締切日に当月分の多くが届く可能性がある（推定）。チャートの案2にある9/4・9/5の山（197,582行・115,434行）がこれかもしれないが、原因は未確認である。

そこで、OKS10は日別のA行数と社員日数に集計してヒントにし、3.2節の記録で測った実際の差分と比べて補正する。

### 2.3 案2：最新を探すコストと、最新を判定できるか

探索コストは、Bronzeの積み上げが単断面の何倍になるかで決まる。9/12時点の評価では案1の138,853行に対し案2は196,179行で、約1.41倍だった。この倍率が月末、締切後、半年後にどう伸びるかを測る。

もう一つ、探索以前の問題がある。**OKS02の差分だけでは、消えた行を検知できない可能性がある。** OKS02は0時間の行を出さず（[サンプルデータ](../research/sample-data.md) 集計7）、全明細を消した日は行そのものがなくなる（8月3日の事例）。差分に現れない行は、Bronzeに古い値のまま残る。案1は入れ替えで自然に消えるので、ここが品質の差になる。同じ社員日の他の明細が変わらない場合にどう判定するかを確かめる。

### 2.4 クエリ費用の桁

チャートの値を合計すると、9月の延べ取得行数は案1が6,881,413行、案2が905,911行で、7.6倍の差がある。ただしバイトに直すと小さい。

| 試算 | 仮定 | 月間のバイト | 費用（$7.5／TiB） |
| --- | --- | --- | --- |
| 案1のCSVを毎日読む | 1行1KB | 約6.9GB | 約$0.05 |
| 案2のCSVを毎日読む | 1行1KB | 約0.9GB | 約$0.01 |
| 案2でBronzeを毎日全行読む | 1,000万行、1行1KB、30回 | 約300GB | 約$2 |

1行1KBと1,000万行は実測ではない仮置きである。行幅が5倍でも月10ドルほどなので、現在の判断ルール「コスト差がわずかなら案1」では案1に落ち着く公算が大きい。決め手は品質と運用になる見込みである。

## 3. 現状分析への要求

### 3.1 最初に確かめること（締切前に開始）

| ID | 問い | 方法 | 分かること |
| --- | --- | --- | --- |
| A-01 | 参照環境は毎日更新されるか。いつ、どう更新されるか | 同じ集計を2回以上比べる。担当者に確認 | 日次記録の可否。資料間で記述が割れている |
| A-02 | OKS02の定義と元テーブルは何か | ビュー定義の参照（権限があれば） | 差分条件に使える列、0時間行が出ない理由 |
| A-03 | 今の権限で何ができるか | ビュー定義、実行計画の参照可否を試す | 使える分析手法の範囲 |
| A-04 | 全行の読取はどこまで終わるか | 月別・会社別に分割して実行時間を測る | ツールの分割単位。全期間では終わらなかった例あり（集計15） |

締切は月初の数営業日に動くとみられる（推定）。サンプルの事例では、OKS02の一括更新が2026-07-01と2026-10-01にある。

### 3.2 日次記録（実測の土台）

本番の取込とは別に、単断面を毎日残しておく。単断面は上書きされるので、この記録だけが「その日の正解」と「実際の差分」を与える。

R-01 毎日6:00相当に、OKS02の全行について識別列と行の指紋（ハッシュ）を保存する。工数の中身や氏名は保存しなくてよい。

R-02 識別は社員日＋照合キー9列とする。OKS02には一意なキーがないため、同じキーの行は連番で区別し、連番が安定するかも記録する。

R-03 2日分の指紋を比べて、新規・更新・消滅を行単位で数える。更新日時が変わらずに中身が変わった行も数える。

R-04 同じ時刻にOKS10の日別件数を取り、2.2節の補正に使う。

R-05 記録は30日以上続ける。締切を最低1回含める。

### 3.3 集計する事実

| ID | 問い | 効く判断 |
| --- | --- | --- |
| A-05 | 作業月別の全件数、月初・月中・月末時点の当月累積件数、1行の実バイト数 | 案1の量、コスト試算の入力 |
| A-06 | OKS10の日別のA行数・社員日数 | 案2の差分量のヒント |

| A-09 | 作業月から見て、値がいつまで動き続けるか | 案1が入れ替わり続ける実害 |
| A-10 | update_dateの時刻基準と精度。実行時刻前後の更新量 | 案2の境界でのもれ |
| A-11 | 消える行の有無と件数。0時間化の差分への現れ方 | 案2の品質 |

出力には、対象ビュー、抽出日時、抽出条件、実行時間を必ず残す。現在のupdate_dateから分かるのは最終更新の分布だけで、後日再更新された行を含む過去の日次件数は復元できない。過去データからの傾向と、日次記録による実測を区別して書く。

### 4.2 正解の定義

R-06 **正解は、同じ日の単断面（OKS02の全行）とする。** 案2で積み上げから取り出した最新が、その日の単断面と明細の単位で一致するかを見る。案1の過去月は、最終的な単断面との差を見る。

R-07 比較は行数と合計工数に加え、明細の内容まで行う。行数・合計の一致は明細内容の一致を証明しない。

R-08 差分は社員日単位で引き出せるようにする。

### 4.3 再生の方法

R-09 日次記録を入力に、方式の処理を1日ずつ実行する。1回ごとに、何を読み、何を書き、結果がどうなったかを記録する。

R-10 取得時刻はパラメータにし、毎日6:00を基準に、時刻を変えた場合も比べられるようにする。

| ID | 場面 | 確かめること |

## 6. 使う技術

接続の制約（DataSpider経由、ビュー読取のみ）は変えられない前提で選んだ。

| 用途 | 技術 | 理由 |
| --- | --- | --- |
| 行の指紋 | SQL ServerのHASHBYTES、またはPython側のSHA-256 | 値の変更を確実に検出する。CHECKSUM系は値が変わっても同じになる可能性が公式に書かれている |
| 保存 | Parquet | 容量が小さく、次の再生で読みやすい |
| 再生 | DuckDB（第一候補） | ローカルで費用なしに何度も回せる |
| BigQueryの実測 | 開発用データセットで実行し、INFORMATION_SCHEMA.JOBSで確認 | 最終候補だけに使う。dry runはクラスタ化テーブルでは上限値しか返さない |
| 差分の比較 | 指紋とSQLのEXCEPT | data-diffは2024年5月にアーカイブ済みのため採用しない |

BigQuery固有で、評価に入れる点が3つある。

- **keijo_dateはそのままではパーティションにできない。** 公式の対象はDATE・TIMESTAMP・DATETIME列と整数範囲で、STRINGは挙げられていない。
- **外部テーブルの読取は課金される。** 現仕様は外部テーブルから取り込むため、CSVの読取バイトが費用に入る。ファイルで絞ったときの課金の減り方は公式に明記がなく、実測する。
- **毎日の置換はストレージに影響する場合がある。** physical storage billingでは、タイムトラベル（既定7日）とフェイルセーフの分が別途課金される。案1に効く。

CDC、Change Tracking、Datastreamは比較の対象にしない。いずれもビューではなくテーブルが対象で、db_owner相当の権限を要する。

R-12 ツールは、SQL Serverへ直接つながらない環境でも動くようにする。SQLファイルを手で流して結果を置くだけでも進められる形を保つ。

R-13 SQLは月別・会社別に分割して実行でき、途中から再開できる。結果のラベルは英数字にする（過去に日本語ラベルの文字化けが起きた）。

R-14 参照環境への負荷を増やさない。全行の読取は1日1回までとする。

R-15 ツールは `tools/` の規則に従う。フォルダごとに `README.md` を置き、接続情報はファイルに書かない。

## 7. データの扱いとAIとの協働

方式検討でAIに渡すのは、原則として集計結果だけにする。

| 区分 | 列の例 | 扱い |
| --- | --- | --- |
| 個人を特定できる列 | sei_mei、mhi_emp_no、user_id | 保存しない。識別に要る列はソルト付きハッシュにし、ソルトはリポジトリの外で管理する |
| 自由記述 | text_item01〜10、shusei_riyu、shuusei_siji | 保存しない。指紋の計算にだけ使う |
| 集計結果 | 行数、バイト数、分布、差分件数 | リポジトリに保存し、AIに渡してよい |

R-16 AIとの検討は次の順で行う。

1. 分析結果を [docs/research/](../research/) に記録し、事実を「データで確認済み」「仮説」に分ける。
2. AIは結果を読み、弱点の指摘と手当ての提案を行う。指摘は再生で確かめられる形にする。
3. 結論は人が判断し、ADRに残す。不採用案と見直し条件も書く。

## 9. 判断してほしいこと

| 論点 | 暫定スタンス | 判断が要る理由 |
| --- | --- | --- |
| Silverの実績の元データをOKS02へ変えるのか | [図書の点検記録](../research/2026-10-31-document-consistency-review.md) J-01を参照 | 既存のSilver仕様と逆の前提になる |
| 案2で消えた行をどう検知するか | 2.3節を測ってから決める | OKS02の差分だけでは拾えない可能性があり、OKS10を使わない前提と衝突しうる |
| 11月1週の方式確定を暫定決定とするか | 暫定決定にし、締切の実測で確かめる | 11月2週のBronze取込実装が続くため遅らせにくい |
| 日次記録のデータをどこに置くか | 個人情報を除いた指紋を、社内で認められた場所に置く | ローカルPCやクラウドへの保存可否は確認していない |

### 取得元・DataSpider担当への確認事項

1. 参照環境の更新方法と時刻（A-01）。
2. DataSpiderで実現できる抽出条件（日時の差分、重なり窓）。
3. 物理削除の有無と、締切処理がOKS02のどの列を更新するか。
4. 源泉への読取で許される時間帯と負荷。
