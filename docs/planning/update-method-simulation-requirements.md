> [!IMPORTANT]
> **主張：過去の保存履歴から日ごとの単断面を疑似的に作り直せば、締切を待たずに2案と承認ゲートを評価できる。**
>
> 疑似再生で11月1週に第1版の評価を出し、締切を含む実際の日次記録で確かめる。疑似再生では承認の時刻が近似になるため、日次記録を置き換えることはできない。
>
> **急ぐこと：** 次の月次締切は11月初めの見込み。単断面は過去に戻せないので、V_T_OKS02の日次記録を締切前に始める（5.1節）。

## 1. 比べるもの

設計は2本のfactで固定し、作り方を案1・案2で比べる。承認済みの実績は、どちらの案でも社員日単位の承認ゲートで作る。

| 処理 | 案1：単断面の入れ替え | 案2：差分の積み上げ |
| --- | --- | --- |
| 源泉→Bronze | 当月全件を毎日置換。過去月は触らない | 差分を毎日追加 |
| 旧版の保持 | Bronzeに残らない。日次CSVの保管で補う | Bronzeに残る |
| fact_work_latest | 当月分を入れ替え | Bronzeから最新を探す |
| fact_work_actual | 前回の結果＋今日の単断面でゲート判定 | Bronzeから最新を探してゲート判定 |

弱点を補う手当ては派生として試す。

| ID | 内容 | 確かめること |
| --- | --- | --- |
| 案1-a | 前月も締切まで入れ替えを続ける | 月末の空白が埋まるか。増える量 |
| 案2-a | 前回より少し前まで戻って取り直す（重なり窓） | 時刻の境界のもれが消えるか。増える重複 |
| 探索X | 毎回Bronzeの全行から最新を探す | 探索コストの上限 |
| 探索Y | 台帳で対象の日・月に絞る | 台帳の読取量を含めた効果 |
| 探索Z | 最新状態だけを持つ中間表を更新する | 表が増える代わりに読取が減るか |

OKS07は両案共通の別workflowなので、2案の差にはならない。ただし承認ゲートの結果には重ねて評価する。

## 4. シミュレーションの流れ

### 4.1 先に流す単発の確認

設計の前提を崩しうるものを、再生を作る前に確かめる。どれも1本のSQLで済む。

| ID | 確認 | 崩れる前提 |
| --- | --- | --- |
| V-01 | 参照環境は毎日更新されるか。同じ集計を2回以上比べる | 日次記録の可否 |
| V-02 | OKS02で、1社員日の中にstatusが混在する社員日の数 | 承認ゲートの判定単位 |
| V-03 | OKS02の同じ社員日で、insert_dateが揃うか | 保存のたびに社員日の全行が書き直される仮説（Q2・Q5） |
| V-04 | OKS02だけ行がない社員日は、OKS10の採用行がすべて0時間か | ADR-003の未確認の前提 |
| V-05 | 全会社のOKS02の全列同一行の件数 | 重複の扱い |
| V-06 | OKS02のupdate_dateの日別件数 | 締切の山の大きさ。チャートの9/4・9/5の山の説明 |
| V-07 | OKS02の1行の実バイト数（列ごとの合計） | 費用の試算 |
| V-08 | 全行の読取が月別・会社別に分けて終わるか | ツールの分割単位。全期間では終わらなかった例あり（集計15） |

### 4.2 疑似単断面を作る

R-01 対象日Tの6:00時点の状態を、D2から作る。社員日ごとに、shusei_dtがT以前の最新の組を選び、そのA行を明細とする。A行がなければ行なしとする。0時間の行は除く（OKS02が出さないため）。

R-02 statusは近似する。行のupdate_dateがT以前ならその値を使い、Tより後なら承認待ちとみなす。update_dateを承認日時と断定できないので、結果の表には近似と明記する。

R-03 最新日の疑似単断面を、D1の実際の単断面と明細の単位で比べ、再現率を出す。これが疑似再生の信頼度になる。

R-04 締切の更新はD2に現れない。V-06で分かった締切日に、対象月の全行のupdate_dateが動いたものとして、案2の差分に加える場合と加えない場合の両方を計算する。

### 4.3 方式を1日ずつ再生する

R-05 疑似単断面を入力に、1節の方式を1日ずつ実行する。実行ごとに、読んだ行、書いた行、結果を記録する。

R-06 取得時刻はパラメータにする。基準は毎日6:00とする。

R-07 承認ゲートの初期状態は、再生を始める日の正解から作る。実運用の初回補完と同じ扱いである。

### 4.4 正解の定義

| 対象 | 正解 |
| --- | --- |
| fact_work_latest | 同じ日の単断面 |
| fact_work_actual | 同じ時点でD2の全履歴から、[ADR-002](../adr/adr-002-handle-repeated-oks10-change-history-in-silver.md)の手順で作った承認済み状態にD3を重ねたもの |

承認ゲートは6:00の断面しか見ない。正解は保存のすべてを見る。この差が取り逃しの大きさになる。

R-08 比較は行数と合計工数に加え、明細の内容まで行う。行数・合計の一致は明細内容の一致を証明しない。

R-09 差は社員日単位で引き出せるようにする。

### 4.5 問いごとの計算

| 問い | 入力 | 計算 | 出力 |
| --- | --- | --- | --- |
| Q1 | 疑似単断面 | 当月分のうち、前日と中身が違う行の割合。作業月の行が何日後に動かなくなるか | 日別の変化率、落ち着くまでの日数 |
| Q2 | D2、D4 | その日に保存があった社員日の、最後の組のA行数を合計する。D4の実際の差分と比べて補正する | 日別の差分行数、補正係数 |
| Q3 | 再生の結果 | 積み上げと単断面の行数の比を日別に出す。探索X・Y・Zの読取行数を出す | 倍率の推移、読取行数 |
| Q4 | 再生の結果、D3 | ゲートの結果と正解を比べる。維持になった社員日の数と、維持が続いた日数を数える | 一致率、差の分類、維持の件数 |
| Q5 | D2、D4 | 前日にあって今日ない社員日を数える。そのうち差分が届かない社員日を分ける | 検知できない社員日数 |
| Q6 | D2、D1 | 作業月の最終実行より後に変わった行を数える | 行数、工数、案1-aで埋まる割合 |
| Q7 | Q1〜Q3、V-07 | 読取・書込バイトに単価を掛ける。BigQueryの実測で確かめる | 月額、3年累計 |

**Q2のヒントについて。** OKS10の行数をそのまま差分量とすると、ずれが両方向に出る。B行と変更していない明細も数えるので多めになり、承認と締切では履歴が増えないので少なめになる。一方、9/2の事例ではOKS02のinsert_dateが最後の保存時刻で、変更していない明細も同じ値だった。保存のたびに社員日の全行が書き直されるなら、最後の組のA行数でOKS02の差分を近く見積もれる（V-03で確かめる）。

**Q5の見立て。** 同じ仮説が正しければ、差分は社員日の全行で届くので、最後に受け取った分で社員日を置き換えれば、明細の削除は検知できる。検知できないのは社員日の全明細を消した場合である。最新の組がB行だけの社員日は、会社AAA全期間で1,060ある（集計2）。

**Q6の根拠。** 9月分を最後に入れ替えるのは9/30の実行である。月末当日の入力、翌月に入ってからの前月分の入力（作業日20260106の入力が2026-01-08の例あり）、締切のstatus更新（9月分の事例は2026-10-01 10:16）は届かない。

**Q7の見立て。** 9月の延べ取得行数はチャートの値で案1が6,881,413行、案2が905,911行である。1行1KBと仮定すると月$0.05と$0.01で、Bronzeを1,000万行として毎日全行読んでも月$2ほどである。仮定を含むが、桁としてクエリ費用は決め手になりにくい。

## 5. 実測の要求

### 5.1 日次記録

R-10 毎日6:00相当に、OKS02の全行を3節の列で保存する。

R-11 2日分を比べて、新規・更新・消滅を行単位で数える。更新日時が変わらずに中身が変わった行も数える。

R-12 同じ時刻にOKS10を取り、その時点の正解を作れるようにする。OKS10は過去の状態が残らないので、承認の時刻の検証にはこの記録が要る。

R-13 記録は30日以上続ける。締切を最低1回含める。

### 5.2 BigQueryでの実測

R-14 2案の最終候補を開発用データセットで動かし、INFORMATION_SCHEMA.JOBSのtotal_bytes_billedで確かめる。dry runはクラスタ化テーブルでは上限値しか返さないので、効果の測定には使わない。

BigQuery固有で、評価に入れる点が3つある。

- **keijo_dateはそのままではパーティションにできない。** 公式の対象はDATE・TIMESTAMP・DATETIME列と整数範囲で、STRINGは挙げられていない。
- **外部テーブルの読取は課金される。** 現仕様は外部テーブルから取り込むため、CSVの読取バイトが費用に入る。ファイルで絞ったときの減り方は公式に明記がなく、実測する。
- **毎日の置換はストレージに影響する場合がある。** physical storage billingでは、タイムトラベル（既定7日）とフェイルセーフの分が別途課金される。案1に効く。

## 6. 評価の基準

合格の数字は仮置きであり、結果を見て見直す。

| 軸 | 指標 | 基準（仮） |
| --- | --- | --- |
| 品質：最新の入力 | 正解との差の明細数・工数 | 毎日0 |
| 品質：承認済み | 正解との差の明細数・工数 | 締切翌営業日の時点で、説明できない差が0 |
| 品質：鮮度 | 変更がSilverに反映されるまでの日数 | 翌日 |
| 回復 | 欠落・遅延の後、正解に戻るまでの回数 | 比較 |
| 処理量 | 抽出行数と実行時間、実CSV容量、Bronze行数、Silverの読取バイト | 比較。通常日とピーク日を分ける |
| コスト | クエリ、ストレージ、GCS | 比較。単価は比較資料の前提を使う |
| 運用 | 実装の量、再実行の手順、作り直しの手順、監視項目 | 比較。人の時間に換算して費用と並べる |

R-15 単価、行幅、増加率は変更して再計算できるようにし、結論が変わる境目を示す。

## 7. ツールとデータの扱い

接続の制約（DataSpider経由、ビュー読取のみ）は変えられない前提で選んだ。CDC、Change Tracking、Datastreamはテーブルが対象でdb_owner相当の権限を要するため、比較の対象にしない。

| 用途 | 技術 | 理由 |
| --- | --- | --- |
| 行の指紋 | SQL ServerのHASHBYTES、またはPython側のSHA-256 | 値の変更を確実に検出する。CHECKSUM系は値が変わっても同じになる可能性が公式に書かれている |
| 保存 | Parquet | 容量が小さく、再生で読みやすい |
| 再生 | DuckDB（第一候補） | ローカルで費用なしに何度も回せる |
| 差の比較 | 指紋とSQLのEXCEPT | data-diffは2024年5月にアーカイブ済みのため採用しない |

R-16 SQL Serverへ直接つながらない環境でも動くようにする。SQLファイルを手で流して結果を置くだけでも進められる形を保つ。

R-17 SQLは月別・会社別に分割して実行でき、途中から再開できる。結果のラベルは英数字にする（過去に日本語ラベルの文字化けが起きた）。

R-18 参照環境への負荷を増やさない。全行の読取は1日1回までとする。

R-19 ツールは `tools/` の規則に従い、置き場は `tools/update-method-simulation/`（案）とする。接続情報はファイルに書かない。

R-20 出力には、対象ビュー、抽出日時、抽出条件、実行時間を必ず残す。

R-21 AIに渡すのは集計結果とハッシュ化したIDだけにする。分析結果は [docs/research/](../research/) に記録し、事実を「データで確認済み」「仮説」に分ける。AIは弱点の指摘と手当ての提案を行い、結論は人が判断してADRに残す。

## 9. 判断してほしいこと

| 論点 | 暫定スタンス | 判断が要る理由 |
| --- | --- | --- |
| 比較資料の判断ルール「コスト差がわずかなら案1」を、品質の基準を満たすことを前提にするか | 前提にする | クエリ費用の差が小さいと、品質を見ずに案1で決まる |
| 日次記録のデータをどこに置くか | ハッシュ化したデータを、社内で認められた場所に置く | ローカルPCやクラウドへの保存可否は確認していない |
| 11月1週の方式確定を暫定決定とするか | 暫定決定にし、締切の実測で確かめる | 11月2週のBronze取込実装が続くため遅らせにくい |

### 取得元・DataSpider担当への確認事項

1. 参照環境の更新方法と時刻（V-01）。
2. DataSpiderで実現できる抽出条件（日時の差分、重なり窓）。
3. 物理削除の有無と、締切処理がOKS02のどの列を更新するか。
4. 源泉への読取で許される時間帯と負荷。
