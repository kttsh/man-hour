## 用語

| 用語 | 意味 |
| --- | --- |
| 社員日 | 1人（または設備）の1日分。company_cd＋user_id＋keijo_date。承認済みの状態を作り直し、Silverの行を置き換える単位 |
| 照合キー（9列） | wbs_cd・opa_cd・genka_center_cd・katudo_type・kyotenbetu_bunseki_key・mhi_wbs・shokushu_cd・keijo_genka_center_cd・youeki_cd |
| 承認済み | statusが4〜7（確認済・確定済・締切済・経理接続済）。1〜3は承認前 |
| 作業日 | 実際に作業した日。3ビューのkeijo_date。取込日・修正日とは別 |
| 最新の入力 | 承認状態に関わらず、今いちばん新しい入力の状態 |
| 承認ゲート | 社員日の全行が承認済みのときだけ、承認済みの状態を更新する判定 |

## 1. 目的と範囲

Silverはstarスキーマで、承認済み工数実績のfact、最新の入力のfact、その切り口となるdimensionを作る。

| 分析目的 | Silverでの扱い |
| --- | --- |
| 月次実績・社員別明細（誰がどのWBS/OPAに何時間） | 対象 |
| プロセス別工数 | 元のコード・名称を保持する。部署横断の共通分類へは変換しない |
| 工数の偏り | 期間・対象者を絞らない。参照権限は別途設計。稼働可能時間との比較は対象外 |
| 直接費／間接費 | 分類・割合計算をしない（部署別の分析段階で検討） |
| 計上先変更の対応確認 | 対象外（保留）。変更指示の記録がなく、取得元データだけでは判定できない |
| 入力状況の確認（承認待ちを含む最新の入力） | 対象。fact_work_latestで扱い、実績factには混ぜない |

## 2. 決定事項

### 2.1 実績の考え方

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 対象日 | 作業日基準。keijo_date（STRING・yyyymmdd）をDATEへ変換し、修正日・取込日へ付け替えない | 6月に4月を修正しても4月の実績とするため |
| 採用する値 | 未承認の修正は混ぜず、承認後に修正値へ置き換える（例：3→5時間は承認前3時間、承認後5時間） | 要件 |
| 承認判定 | status 4〜7。承認日の有無やupdate_dateでは判定しない | 定数ファイル（KeijoKosuConstants.java）でstatusの意味が確定 |
| 2つの見え方 | fact_work_actual（承認済み）とfact_work_latest（最新の入力）を分け、合算しない。粒度・キー・dimensionは揃える | 別の問いのため（ADR-003） |
| 元データ | V_T_OKS02の単断面を元にし、締切後の修正はV_T_OKS07で反映する。V_T_OKS10は日次処理に使わず、差分量のヒント、検証、初回の補完に限る | ADR-003。OKS02は締切後の修正をほぼ反映しないため、OKS07を重ねる（調査まとめ） |
| 承認ゲート | 社員日の全行がstatus 4〜7なら今日の行で置換、承認待ちを含めば前回の承認済みを維持、全件の単断面に行がなければ実績なし | OKS02には旧版が残らないため、Silverで保持する |
| 置換範囲 | 社員日まるごと作り直して置き換える | 分割・付け替え・全削除でも古い明細が残らないため（A4時間→A1・B2・C1時間でも旧A4時間が残らない） |
| 0時間 | 修正を重ねた後に除外。NULLは0とみなさない | 先に除くと旧実績が残るため。OKS02は0時間の行を出さないが、OKS07の修正で0時間になる行がある |
| 設備の行 | machine_flg＝1の行も残し、人の分析では利用側で除く | 原価・設備の分析に使える可能性があるため |
| 単位 | keijo_kosuは時間単位（2.0＝2時間、0.5＝30分）。ビュー間・修正前後・複数回受信を単純加算しない | 二重計上を防ぐため |

### 2.2 粒度とキー

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| fact型 | 2本とも最新状態のトランザクションfact。スナップショットfactは作らない | 締切時点への切替は不要のため |
| 粒度 | 1行＝入力明細1件（社員日＋照合キー9列） | 全16社で、ほぼ1行に決まることを確認（サンプルデータ 集計15） |
| 作業分類 | 同じ社員・作業日・計上先でも、作業分類（ミーティング・教育など）が違えば別行（必須） | 作業分類の区別をSilverで失わないため |
| 明細の合算 | 別の入力明細は合算しない。同じ照合キーの明細が複数あれば別行のまま例外として扱う | 工数システムは二重入力を防いでいないため |
| 主キー | 社員日＋9列＋連番のハッシュ値（サロゲートキー）。社員日＋9列は主キーとして保証しない。同じ明細は2本のfactで同じ値になる | 取得元に明細ごとの不変IDがなく、作り直してもIDを変えないため |
| hnko_rireki_id | 明細の識別に使わない | 保存のたびに新しい値になるため |

### 2.3 dimensionと属性

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 社員 | company_cd＋user_idで識別。mhi_emp_noは作業日当時の値として保持 | ADR-001 |
| 所属 | 明細の所属コード・所属名をそのまま使い、現在の所属で付け替えない。履歴は持たない | 異動前後の少しのずれは受け入れる |
| 計上先・作業分類の名称 | 明細の元の値をそのまま持ち、集計・結合はコードで行う。名称の履歴マスタは持たない | 同じコードでも明細ごとに名称が違う場合があるため（サンプルデータ 集計16） |
| 作業分類 | 拠点別分析キー単独で識別。活動タイプとは別の切り口。空欄は除外せず「未設定」 | 活動タイプが同じでも分類が分かれるため |
| MHI WBS・職種 | dimensionにせず、factの列として持つ | 名称は明細の値のため、別表にする利点が小さい |
| 計上先 | WBS・OPA・原価センタを種別で区別する統合dimension案 | コードだけで同一視しないため |
| NULL・空白 | 照合キー・IDの計算時だけ、NULL・空文字・空白のみを空文字にそろえ、前後の空白を除く。列には元の値を残す | — |

### 2.4 取得回をまたぐ重複

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| OKS02の同じ取得回の全列同一行 | 1行にまとめ、元の行数を列に残す（Bronzeは変更しない） | ADR-002の部分決定の考え方を引き継ぐ |
| OKS02の取得回をまたぐ同じ明細 | 案2の場合、社員日ごとに最後に受け取った状態を使う（案1は入れ替えるので起きない） | 同じ明細の旧版を二重に数えないため |
| OKS07の取得回をまたぐ同じ修正 | 社員日＋9列＋correction_numごとに最後に受け取った行を使う | 承認待ち→承認済みの古い状態と二重に数えないため |
| 順序の基準 | _loaded_at。_batch_id・snapshot_dateでは決めない | Bronzeの管理列の定義に合わせるため |

OKS10を検証や初回の補完に使うときは、ADR-002の整理に従う。

### 2.5 例外の扱い

ルールどおりに処理し、記録して件数で監視する。

- 社員日の中でstatusが混在する → 承認待ちとみなし、前回の承認済みを維持する。
- 承認前の修正の後に承認済みの修正がある → 承認前の修正だけを読み飛ばす。
- 照合キーが1行に決まらない明細に修正が当たる → 同じキーの行をすべて修正後の1行に置き換える。
- 修正前工数が直前の承認済みの値と合わない → 確認せずにそのまま置き換える（入力間違いの修正で合計が変わることもあるため）。

## 3. 前提と注意点

- fact_work_actualは前回の結果に依存する。作り直すには日々の単断面を保持する必要がある（案1は日次CSVの長期保管、案2はBronzeが履歴を兼ねる）。
- 行が消えたと判断するのは、その日の全件の単断面に行がないときだけ。削除の承認待ちと承認済みは区別できない。
- 同じ日に承認と再編集が続くと、旧承認値を取り逃す。
- 記録開始時に再編集中の社員日は、OKS10で補う。
- correction_kbnは1＝締切前に0時間より多い工数があった明細、0＝締切前にないか0時間の明細と推測しているが、正式な定義は未確認。構築手順はcorrection_kbnに依存しない。
- サロゲートキーは、コード体系の変更やuser_idの切替でIDが変わる。消した明細を同じ内容で再入力すると同じIDが復活する。
- CSVが届かないことだけで取消・削除と判断しない。部内サンプルの分類を全社に一般化しない。
