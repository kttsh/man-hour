## 3. fact_work_actual

### 3.1 粒度とキー

- **粒度**：社員日（company_cd＋user_id＋keijo_date）＋照合キー9列（wbs_cd・opa_cd・genka_center_cd・katudo_type・kyotenbetu_bunseki_key・mhi_wbs・shokushu_cd・keijo_genka_center_cd・youeki_cd）。
- **主キー**：社員日＋9列＋連番のハッシュ値（SHA-256など）。連結の書式とハッシュ関数は詳細設計で定義する。
- **連番**：同じ照合キーの明細が2行以上あるときだけ使う。並び順はinsert_date → keijo_kosu → テキスト項目。それでも区別できなければ例外とする。
- 工数だけが変わった明細は同じID、計上先を付け替えた明細は新しいIDになる。
- 同じ照合キーの明細が複数あれば、合算せず別行として残す（会社AAA全期間で13キー・26行）。

### 3.2 列（候補）

| --- | --- | --- |
| actual_detail_key | STRING | 主キー（3.1のハッシュ値） |
| key_version | INT64 | IDの作り方のバージョン |

### 3.3 作成手順（方針案）

1. **対象の社員日を選ぶ**：前回の処理より後に、OKS02の行が変わった社員日、全件の単断面から行が消えた社員日、OKS07の新しい行に出てくる社員日。
2. **入力を整理する**：OKS02は同じ取得回の全列同一行を1行にまとめ（元の行数を残す）、案2では社員日ごとに最後に受け取った状態を使う。OKS07は社員日＋9列＋correction_numごとに最後に受け取った行を使う。
3. **承認ゲート**：社員日ごとに判定する。
   - 全行がstatus 4〜7 → 今日の行を採用
   - status 1〜3の行を含む → 前回の承認済みを維持し、件数を記録
   - 全件の単断面に行がない → 実績なし
4. **締切後の修正（OKS07）**：status 4〜7の修正をcorrection_numの小さい順に、照合キー9列でkeijo_kosuに置換・追加する。status 1〜3の修正は読み飛ばす。複数明細に当たる修正は、同じキーの行をすべて修正後の1行に置き換え、例外として記録する。OKS02は修正をほとんど反映しないため、手順3で採用した行にも当て直す。維持した社員日に新しい修正が届いたら、維持している状態に重ねる。
5. **0時間を除外する**（NULLは0とみなさない）。
6. **IDを計算し、dimensionを参照する**。結合前後の件数・工数と、参照先の一意性を検査する。
7. **社員日まるごと一度に置き換える**。結果が0行ならその社員日の行はすべて消える。明細IDで結合する下流の表も社員日単位で作り直す。
8. **処理済みの印**（今回使った_loaded_atの最大値）を記録し、次回の手順1に使う。

手順3の維持は前回の結果に依存する。作り直すときは、保持している日々の単断面を古い順に再生する。

一度に入れ替える方法、順位式とSQLは詳細設計で定義する。

## 4. fact_work_latest

### 4.1 粒度とキー

fact_work_actualと同じ粒度・同じ主キーの作り方とする。同じ明細は2本のfactで同じキーになる。2本を合算しない。

### 4.2 列（候補）

fact_work_actualの列に次を加える。

| 列（名前は仮） | 型案 | 内容 |
| --- | --- | --- |
| status | 元の型 | 採用した行のstatus |
| is_pending | BOOL | status 1〜3の行か |

### 4.3 作成手順（方針案）

1. **対象の社員日を選ぶ**：fact_work_actualの手順1と同じ。
2. **入力を整理する**：fact_work_actualの手順2と同じ。
3. **今日の行を採用する**：statusで絞らない。全件の単断面に行がなければ、その社員日の行はなし。
4. **締切後の修正（OKS07）**：status 1〜3の修正も含めて、correction_numの小さい順に重ねる。
5. **0時間を除外し、IDとdimensionを処理し、社員日まるごと一度に置き換える。**

### 4.4 比較ビュー（候補）

2本のfactを主キーで突き合わせ、承認待ちによる差の明細と工数を出す。差を見るための手段であり、factとしては持たない。
